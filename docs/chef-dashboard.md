# Chef dashboard

The existing `/chef/dashboard` page now reads an authenticated, consolidated kitchen projection from PostgreSQL. No production statistics, orders, activity, or chart measurements are seeded or generated by the dashboard. Controlled SQL records and serialized service responses live only in tests.

## Features

- Six summary cards: today's receipts with yesterday comparison, live pending/preparing/ready counts, today's completed orders, and measured preparation time.
- An oldest-first kitchen queue with server-side status filtering and pagination, receipt age, table/floor, quantities, preparation notes, inline details, and valid actions supplied by the backend.
- The next eight confirmed reservations, sorted by arrival, including assigned tables/floors and saved preorder dishes without customer or payment details.
- Hourly order volume for today, daily volume for the last seven or thirty days, current status distribution for the same receipt cohort, and seven days of measured preparation performance.
- Kitchen performance and persisted activity, loading skeletons, empty and error states, retry/manual refresh, and the existing theme toggle.
- Responsive desktop, tablet, and mobile layouts, native keyboard controls, accessible chart labels/tooltips, and scrollable charts that do not overflow the page.

## API and authorization

`GET /api/chef/dashboard?period=today&status=ACTIVE&page=1&page_size=8`

| Parameter | Accepted values |
| --- | --- |
| `period` | `today`, `last7`, `last30` |
| `status` | `ACTIVE`, `PLACED`, `ACCEPTED`, `PREPARING`, `READY` |
| `page` | Integer, at least 1; clamped to the final available queue page |
| `page_size` | Integer, 1–50; UI uses 8 |

The endpoint uses the existing `current_chef` JWT cookie dependency, including active-account, suspended-restaurant, and temporary-password restrictions. Restaurant scope comes from the existing chef → manager → restaurant relationship using `staff_restaurant`. A supplied restaurant ID cannot change that scope. Every aggregate, queue, seating, reservation, and event query is restaurant-scoped. The Pydantic response includes only kitchen fields and allowlisted food snapshot fields.

Actions reuse `PATCH /api/chef/orders/{order_id}/status`. The dashboard derives `allowed_actions` directly from `CHEF_TRANSITIONS`, so it introduces no parallel transition policy. Existing row locks, transition checks, timestamps, persisted events, and notification behavior remain intact. The UI locks each order while an action or confirmation is pending, confirms ready/served changes, and reconciles from REST after success or failure. Post-mutation reads cancel an earlier read to avoid rendering pre-mutation state.

The existing workflow reserves acceptance for the manager. Chefs can move `ACCEPTED → PREPARING → READY → SERVED`; placed orders display “Awaiting manager acceptance.” No new chef acceptance permission or completion permission was added.

## Data definitions

| Metric or section | Source and calculation |
| --- | --- |
| Today's orders | `FoodOrder.created_at` in today's restaurant-local midnight interval, including subsequently cancelled/rejected orders |
| Yesterday comparison | Same receipt calculation for the full previous local day; percentage is unavailable when yesterday is zero |
| Pending orders | All currently `PLACED` or `ACCEPTED` restaurant orders, including prior-day receipts |
| Preparing / ready | All currently `PREPARING` / `READY` restaurant orders, including prior-day receipts |
| Completed orders | Currently `COMPLETED`, grouped by `completed_at`; historical rows without it use receipt date, as disclosed in the page methodology |
| Average preparation | SQL average of `ready_at - preparation_started_at`, in minutes, for orders currently `READY`, `SERVED`, or `COMPLETED` and ready today; requires both timestamps and `created_at ≤ preparation_started_at ≤ ready_at ≤ as_of` |
| Prepared today | Count of those kitchen-finished statuses with `ready_at` today; rows missing a valid start still count as prepared but do not enter the average |
| Order volume | SQL counts by local creation hour/day; genuinely empty buckets are zero-filled |
| Status distribution | Current statuses of orders received within the selected analytics period; includes placed, accepted, preparing, ready, served, completed, cancelled, and rejected |
| Preparation chart | Seven SQL aggregates by local ready date; missing measurements stay `null` and render as N/A rather than zero |
| Longest active age | Current instant minus the minimum active `created_at`; elapsed ages are rendered from server-derived durations |
| Priority | Rank by actual receipt time across the full active queue, before status filtering; no invented service target |
| Upcoming reservations | Next eight future `CONFIRMED` arrivals from `Reservation`, with `ReservationTable`, `DiningTable`, `RestaurantFloor`, and allowlisted saved `preorder_items` |
| Recent activity | Up to twelve persisted `RealtimeEvent` rows for restaurant order events; no activity is fabricated from order `updated_at`. Events with a recorded previous status show the actual transition. Ambiguous initial accepted/placed event snapshots say “Order status recorded”; payment-only snapshots without a transition to another status are omitted |

Daily boundaries follow the project's existing `Asia/Kolkata` business timezone through `table_availability.RESTAURANT_TIMEZONE`. Queue timestamps are timezone-aware. The date-range selector changes the two receipt analytics charts; summary cards, performance, reservations, and the queue remain current.

Aggregations execute in SQL. Only bounded queue, reservation, and event previews reach Python. Table/floor assignments are loaded in batches, avoiding per-order relationship queries. The queue-growth tests verify a fixed query count (at most twelve aggregate/preview queries without seating lookups); seating adds at most two batch queries. Existing order/date/status indexes are reused. No migrations or dependencies were added.

## Live synchronization

The dashboard uses the shared, cookie-authenticated `GET /api/events/stream` connection through `useRealtimeEvents`. Its existing backend restaurant authorization remains the event boundary. Order and booking events are deduplicated and coalesced for 500 ms before a REST refresh. Initial stream readiness and reconnection reconcile from REST.

A visibility-aware 30-second reconciliation poll covers missed events, connection failure, and local date rollover. Focus/visibility restoration refreshes stale data. Same-filter concurrent requests coalesce, changed filters cancel obsolete requests, and request timeouts are 15 seconds. Timers, event subscriptions, requests, and listeners are cleaned up on unmount. Transient errors label retained data as stale and pause order actions; authentication/authorization errors clear the data.

## Existing data limitations

- Restaurants have no per-restaurant timezone setting, so analytics preserve the existing Asia/Kolkata rule.
- There is no configured preparation deadline/threshold. Delayed-order counts are unavailable rather than fabricated.
- Historical orders missing preparation timestamps cannot contribute measured durations. No fallback uses `updated_at`, receipt-to-completion estimates, or a configured menu estimate.
- Historical completed rows missing `completed_at` use receipt date for the completed card; that limitation is explicitly disclosed.
- The existing event source sometimes emits an accepted/placed status snapshot without distinguishing order creation from payment confirmation. Such entries are labeled as recorded status rather than invented acceptance events.
- Reservations that are already seated are represented through active kitchen orders; the planning preview shows future confirmed arrivals only.
